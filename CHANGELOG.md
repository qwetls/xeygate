# Changelog

All notable changes to **XEYGATE** are documented in this file.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **Admin top-up toggle** — a new `topup_enabled` system setting (default: on) lets admins disable wallet top-ups without affecting existing balances. When off, `POST /v1/users/topups` returns `403 { code: "topup_disabled" }`. The toggle is exposed in **Admin → Settings → Security** as an ON/OFF segmented control alongside the existing auth and creator-application toggles. No schema migration required — stored in the existing `system_settings` key-value table.
- **DB-backed plan configuration with an admin editor** — the plan limits that `EnforcePlanAccess` enforces on every `/chat/completions` request (daily token budget, requests/minute, model-tier access) and the plan price now live in a new `plan_configs` table instead of being frozen into `packages/constants`. The table self-seeds from the code defaults on first boot, so fresh and existing databases both just work. Admins edit everything live from the new **Plans** page (`/admin/plans`, sidebar entry under Workspace): per-plan name, price, `rpm`, `daily_tokens` (0 = unlimited), and model access tier (`starter` / `pro` / `pro_max`) — saved config takes effect on the next request, no redeploy. Backed by `GET /v1/admin/plans` + `PUT /v1/admin/plans/:plan` (validated, admin-only) and a public `GET /v1/plans`; the public `/plans` marketing page now renders price and limits from that endpoint, falling back to the static copy only while the request is in flight.
- **Sandbox payment gateway — top-ups settle without admin approval** — the wallet top-up flow is now `create order → pay → credited`, end to end, by the buyer. New orders are created as `pending_payment`; the Billing page shows a **Pay $X** button that settles through `POST /v1/users/topups/:id/pay`, which credits the wallet and writes the ledger row in the same step. Money moves through exactly one code path (`SettleTopupOrder`) so a real gateway webhook can call it unchanged later; double-settle is impossible because the status flip is a conditional `UPDATE ... WHERE status IN ('pending','pending_payment')`. The gateway is reported to the client on order creation (`gateway: { name: "sandbox" }`). `/admin/topups` becomes a read-only payment log (audit + Open Orders / Unpaid Total stats), and `POST /v1/admin/topups/:id/process` stays as a manual-correction escape hatch — pre-existing `pending` orders remain processable.
- **Admin plan management** — `PATCH /v1/admin/users/:id/plan` lets admins assign any plan to a user (retained for future creator tiers). Plan enforcement on `/chat/completions` is disabled — XEYGATE operates as a credits-based marketplace, not a subscription platform.
- **Simplified client key creation** — the client-facing API key creation dialog now only asks for a key name and status toggle. Admin-only fields (`rate_limit`, `quota_limit`, `credit_limit`, model selector) are removed from the client dialog (they remain in admin key management).
- **Full marketing landing page** — the landing page now features live marketplace analytics charts (traffic, latency, token volume) powered by recharts and the public `/v1/analytics/*` endpoints, a model leaderboard showing top models by request volume with success rates, a supply endpoints panel with official/creator badges, and all stats bands pulling real data from the catalog and analytics APIs.
- **Embedded documentation site** — `/docs` with sidebar navigation (Getting Started, Core Concepts, Marketplace, Reference) and `/docs/api-reference` with a complete endpoint reference covering all 40+ API routes across Chat Completions, Models, Catalog, Analytics, Auth, Profile & Billing, Creator, API Keys, Logs, Quota, and Admin sections. Each endpoint shows method, path, description, and auth requirement.
- **Unicorn-grade web security hardening** — API response headers now include `Strict-Transport-Security` (2-year max-age + preload), `Content-Security-Policy` (strict self-only policy), `Permissions-Policy` (camera/microphone/geolocation/FLoC denied), `Cross-Origin-Opener-Policy` (same-origin), `Cross-Origin-Resource-Policy` (same-origin), and `Cross-Origin-Embedder-Policy` (require-corp). Session cookies upgraded to `__Host-` prefix (enforced HTTPS-only, domain-scoped, no Path escape), `X-XSS-Protection` corrected to `0` (modern CSP supersedes the legacy header), and `SROUTER_SECURE_COOKIES` toggle removed in favor of always-on `secure: true`.
- **Cookie consent banner and Cookie Policy page** — bottom-of-viewport consent banner (dismissable, persisted to localStorage) linking to the new `/cookies` legal page. Cookie Policy documents all cookies used, their security attributes (`__Host-` prefix, HttpOnly, Secure, SameSite=Lax), and what XEYGATE does *not* track. Cookie Policy cross-linked in the legal pages footer and landing page footer.
- **Upstream errors are sanitized behind a trace id** — a provider running out of credit, rate-limiting, or timing out used to hand the buyer the raw upstream body verbatim (every executor frames failures as `<Name> Provider Error (NNN): <body>`, and all six client-facing paths echoed it — chat streaming/non-streaming, messages streaming/non-streaming, images, and the global error handler). Clients now receive one well-formed sentence chosen by status (`This model is temporarily unavailable.`, `The upstream provider is at capacity. Please retry in a moment.`, …) suffixed with `(ref: xg-1f2e3d4c)`, while `LogUpstreamFailure` writes the real message and stack to the server log under that same id and the id travels back as `X-Request-Id` — so a support report maps to a single `grep`. The two messages XEYGATE authors itself (model disabled by an admin, model has no route) stay verbatim, because those are not upstream leaks.

### Changed
- **Landing page de-slopped** — the marketing page leaned on the visual tells that make a site read as machine-generated: leetspeak in six kickers and headings (`USE C4S3S`, `F3ATUR3S`, `BUILD W1TH XEYGATE`, `SW1TCH PR0V1D3R — JUST TH3 PR3FIX`), a seven-item ALL-CAPS keyword ticker pinned above the nav, a shimmering gradient headline, two `blur-3xl` emerald glow blobs, a Sparkles badge pill, and fake macOS traffic lights on the code block. All of it is gone, along with the now-dead `animate-marquee` and `animate-shimmer-text` CSS. What stayed is the part that was never decoration: the live analytics section (real `/v1/analytics/*` data), the quickstart samples carrying real model ids, and the concrete operational details (`sr-live-*` keys, quotas, combo routing, served-by tracing). The page is 112 lines lighter.
- **Landing page restructured and rewritten** — removing the decoration exposed the real problem: three sections in a row followed one template (centred eyebrow, centred heading, centred paragraph, uniform six-card grid) inside a narrow `max-w-5xl` column, so the page read as a document rather than a product. The hero is now a two-column split with a live stats panel (models, providers, 24h requests, latency) beside the headline; section headers are left-aligned with the description set beside the title rather than under it; the container widened to `max-w-6xl`. Copy now says something specific: the hero headline went from "One endpoint for every AI model" — a category description any gateway could print — to "Every model behind one key.", and the subhead names the actual providers plus the two facts that distinguish the gateway (quotas enforced per key, every request logged with the connection that served it). Section titles lost their tricolons ("Built for AI apps, agents, and product teams" → "What gets routed through it", "The gateway" → "What one key gets you"), and CTA labels are sentence case throughout.

### Fixed
- **Manage button in Quotas & Limits navigates to wrong URL** — the Manage link used the provider display name (e.g. "B.AI") instead of the base id ("bai"), so clicking it landed on a non-existent provider page. `ProviderQuotaAccount` now carries a `providerId` field (the canonical base id) set by both live OAuth fetchers and usage-logged accounts, and the frontend uses it for the `/admin/providers/$providerId` route.
- **Version constants stuck at v1.5.0** — `GLOBAL_VERSION`, `APP_VERSION`, and `API_VERSION` in `packages/constants/src/version.ts` were not bumped with the v1.6.0 release; the settings page displayed v1.5.0 on the live instance.
- **Marketplace offered account-creation buttons to signed-in visitors** — `/catalog` and its model detail page hardcoded `/register` CTAs ("Become a creator", "Register to buy or sell", "Get your own key") with no awareness of the session, and `/register` carries no auth guard, so a signed-in buyer clicking **Become a creator** was handed the sign-up form and read it as "logged out again". Both pages now read the session through `useSessionUser()` (sharing the portal's `user-auth-status` cache key, so no extra `/v1/users/me` round-trip) and send signed-in users to `/dashboard`. The session itself was never broken.
- **The model denylist never matched vendor-qualified listings** — after the display-id migration `custom_models.model_id` stores `xeygate/neko/hy3` while `disabled_models.model_id` still stores the bare `hy3`, so the pair lookup never hit and the catalog advertised models whose every request was then rejected with `ModelDisabledError`. `IsModelDisabled` and the catalog's `EnabledListings` filter now compare both the stored id and its display form.
- **Deleting a provider orphaned its marketplace listings** — `deleteProviderDB` cleaned `disabled_models` but left `custom_models` rows behind, and because listings are inherited by base id a deleted connection's row kept surfacing as a phantom storefront card through any surviving clone of the same driver. Deletion now clears both tables, with a regression test.
- **Every upstream rejection reached clients as HTTP 500** — `InferenceErrorStatus` never parsed the status out of the `Provider Error (NNN)` framing the executors emit, so a provider's 402 (out of credit) or 429 (rate limit) was flattened into an internal-server error, breaking any client that branches on status. The status is now read from that framing, ahead of the loose text heuristics.
- **Deploy workflow passed an input `appleboy/ssh-action` v1 no longer declares** — `script_stop` was removed in v1, so every deploy emitted a warning annotation while the flag did nothing. Removed, with a note that the script's own `set -e` is what aborts the deploy on the first failed command.
- **Fresh installs wrote a malformed `.env`** — the `JWT_SECRET` fallback chain was joined with `;` instead of `||`, so the uuid fallback ran even when `openssl` succeeded and its embedded newlines landed in `.env` as junk lines (docker compose parses that file as `env_file`). It is now a single `||` chain that yields one line of 32 bytes of hex either way.

## [1.6.0] - 2026-09-15

### Added
- **Per-request connection audit (`served_provider_id`)** — bulk pools (one driver, hundreds of keys) had no way to show which key actually handled a call: `request_logs.provider_id` only ever stores the routing identity (`bai`), and the `resolved_model` column was plumbed end to end but never populated. Every completion now records the concrete connection that served it (`bai-1789023519492-37`) in a new `served_provider_id` column — the registry reports the winning candidate back through an optional callback on `chatCompletion`/`chatCompletionStream`, streaming and non-streaming alike — and the log detail modal shows a **Served By** panel. Makes round-robin spread across a pool auditable with one query (`GROUP BY served_provider_id`) instead of guesswork.
- **Creator application form + admin applications toggle** — becoming a creator is no longer a one-click upgrade. Admins now control a **"Open Creator Applications"** toggle in admin settings (default **closed**); while closed, `PUT /v1/users/role` rejects new applications with `403 creator_applications_closed` (existing creators and pending requests are untouched). When open, applicants fill a short form — brand/display name, what they plan to offer, optional link — persisted in a new `creator_applications` table, validated for length (80/2000/300 chars) and shown to admins in a dedicated "Creator applications" panel on `/admin/users` next to Approve/Reject. Applicants can read their own submission back via `GET /v1/users/creator-application`.

### Fixed
- **My APIs no longer shows "0 models listed" for official connections** — `GET /v1/users/my-providers` counted only connection-scoped `custom_models` rows, so bulk-imported connections (one key per row, models stored under the shared base id) always reported zero. The count now inherits base-id catalog rows the same way the marketplace does — own rows plus base-id rows, deduplicated.
- **Same model across endpoints is now one marketplace entry** — the flat model list (`GET /v1/catalog/models`) grouped by each provider's stored listing id, so one model listed on two endpoints appeared as two storefront entries (`hy3` vs `neko/hy3`) purely because of a prefix. Entries now group by bare model id: the prefix-free id stays canonical and requestable, prefixed variants survive as `aliases` that still resolve through the `?model=` detail lookup, and offers from every endpoint merge into one entry with the cheapest highlighted. Routing is untouched — it still matches each connection's stored id.
- **Slash-id entries no longer list themselves as their own alias** — when an entry's canonical id contains a slash (e.g. `cx/gpt-6-astra`), the bare-id extraction would push the entry's own id into its `aliases` array. Entries now filter themselves out of their alias list.

## [1.5.0] - 2026-09-12

### Added
- **GitHub sign-in** — visitors can create an account and sign in with their GitHub account via a "Continue with GitHub" button on `/login` and `/register`, gated by the same Terms & Privacy checkbox as the email flow. The OAuth round-trip (`/v1/users/oauth/github/start` → GitHub → `/v1/users/oauth/github/callback`) is CSRF-guarded by a state cookie, stores the GitHub id on the account, and **links to an existing account with the same email** instead of creating a duplicate. It honors every existing rule: the admin registration gate (new GitHub accounts land as `pending` when enabled), bans, and server-side terms consent (new accounts are stamped from the checkbox flag; pre-consent accounts re-accept through the same flow). Subsequent GitHub sign-ins count as sign-ins for the daily login streak; accounts created through GitHub are registrations and never grant it. Falls back to the `ID+login@users.noreply.github.com` address when the profile email is private. The button hides itself (`GET /v1/users/oauth/github/status`) until the instance is configured with `GITHUB_CLIENT_ID` + `GITHUB_CLIENT_SECRET` for a GitHub OAuth App whose callback URL is `https://<host>/v1/users/oauth/github/callback`.

## [1.4.0] - 2026-09-12

### Added
- **Server-side terms consent** — the sign-up/sign-in checkbox is now enforced by the API, not just the UI. `POST /v1/users/register` rejects bodies without `accepted_terms: true` (`400 terms_not_accepted`) and stamps the new-account row with `accepted_terms_at` + `terms_version`; accounts created before the consent record (or consented to a stale ToS version) must re-accept once at `POST /v1/users/login` (`403 terms_required`) before a session is issued. `GET /v1/users/me` exposes both fields. Operator accounts (env bootstrap, legacy `admin_account` migration, first-run `/admin/bootstrap`) are stamped at provisioning time so admins are never locked out.

### Fixed
- **Marketplace no longer leaves the portal shell** — clicking **Marketplace** in the client/admin sidebar navigated to `/catalog`, a public standalone page with its own header; the sidebar and topbar vanished, making it feel like exiting to an external page. Signed-in users (any status except banned) now get `/catalog` rendered **inside** the client shell — the navbar stays put with Marketplace active in the breadcrumb — while anonymous visitors keep the original standalone storefront. The portal shell was extracted into a reusable `ClientShell` component shared with the `_client` layout.

## [1.3.0] - 2026-09-12

### Added
- **Public legal pages** — `/terms`, `/privacy`, `/acceptable-use` and `/refund`, written for how XEYGATE actually operates (prepaid credit wallet, admin-confirmed top-ups, third-party model routing, creator marketplace). Shared `LegalShell` layout with cross-links and a **Legal** column in the landing footer; sign-up and sign-in are gated by a required "I agree to the Terms of Service and Privacy Policy" checkbox (submit stays disabled until checked).
- **Client Billing page** (`/dashboard/billing`) — wallet balance hero, top-up orders (preset $10/$25/$50/$100 or custom $5–$10,000 with an optional payment reference), the buyer's order history, and the full transaction ledger (`GET /v1/users/transactions`, previously API-only) with load-more paging.
- **Top-up order flow** — buyers create an order and pay out-of-band (`POST /v1/users/topups`, one pending order per user, `POST /v1/users/topups/:id/cancel`); an admin reviews them at `/admin/topups` and **Approves** (wallet credited + `credit` ledger row, processed exactly once via a conditional state flip) or **Rejects** with a note. New endpoints: `GET /v1/admin/topups`, `POST /v1/admin/topups/:id/process`.

### Removed
- The simulated `POST /v1/users/credits/topup` MVP endpoint (added credits directly with no ledger entry and no payment step) — superseded by the order-based flow.

## [1.2.0] - 2026-09-11

## [1.1.0] - 2026-09-11

### Added
- **Daily Login Rewards** — signing in credits the account wallet automatically: **+$8 on days 1–6 of a login streak, +$10 on day 7**, after which the cycle restarts. Granting is keyed to the UTC calendar day (extra logins the same day never double-credit); skipping a day resets the streak to day 1. Every reward lands as a `credit` row in the wallet ledger (`Daily login reward — day N of 7`) and is reported in the `POST /v1/users/login` response (`dailyReward`) with a toast on the dashboard sign-in page.
- **Sliding web sessions** — an authenticated request made while a session is under half its 30-day window refreshes it back to the full 30 days, so active users are never bounced to the login page mid-work; idle sessions still expire. (`packages/db` `user_sessions`)
- **Marketplace in navigation** — `/catalog` link added to both the admin sidebar and the client sidebar (the landing page already linked it).
- **Cache-Control on the SPA** — the HTML shell is served `no-cache` and hashed `/assets/*` files `public, max-age=31536000, immutable`, so a deploy actually reaches browsers instead of pinning a stale bundle (the SPA fallback HTML is excluded from the immutable rule).
- `GET /v1/quota` now reports a second tier of provider accounts (`quotaType: "usage_logged"`) aggregated from the 30-day request logs for every enabled provider without a live OAuth quota fetcher, so Quotas & Limits reflects real connected supply instead of only OAuth-supported drivers.

### Fixed
- **Playground model picker 500** (`e.filter is not a function`) — `ModelsLogic.List` awaited the combo-merge only outside the `"all"` scope, so the disabled-model filter received an unresolved Promise whenever at least one model was denylisted. `/v1/models` is now stable with an active denylist (regression-tested against the exact production trigger).
- Login/register/`change-password` session cookies now honor `SROUTER_SECURE_COOKIES` (previously the user-facing paths hardcoded `secure: false` while only the admin bootstrap respected the flag).

## [1.0.0] - 2026-09-09

### Added
- Initial public release of XEYGATE: cloud-first AI gateway with OpenAI- and Anthropic-compatible endpoints, multi-provider OAuth/API-key connectivity with background token refresh, failover & combo routing, virtual API keys with quota/credit limits, request logs & analytics, Cloudflare Tunnel support, the model-centric public storefront (`/catalog`), marketplace namespaces (`/user/v1`, `/official/v1`), creator listings with wallets & payouts, admin user management with account-based admins, bulk API-key import, and server-side model disable.
